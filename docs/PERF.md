# reflux 的性能实测

这份文件是**一次运行**的记录，不是承诺。方法在 `tools/measure.py` 里，任何人都能在自己的机器上重跑：

```
python3 tools/measure.py                      # 四段全跑（约一分钟，两段要 chromium）
python3 tools/measure.py --only bytes,mutations
```

数字只在同一台机器上横向比较有意义；跨机器比绝对值没有意义，比**方法**才有。

## 本次运行的机器

```
Linux 6.18.55 x86_64 · 16 核 · Python 3.14.7 · 无头 chromium（CDP）
运行日期：2026-10-20 · 仓：M1.7 + T9 之后（一个页面、一套方言）
```

## 一、一个回合在线上占多少字节

`wire.draw` 出来的一帧，JSON、UTF-8、不含 WebSocket 帧头。回合取自参考应用 `reflux/demo_app.py`
实际会发的那些。

| 回合 | 字节 | 字符 |
|---|---|---|
| 回声（`set`） | 171 | 171 |
| 加一行（`append`） | 392 | 386 |
| 删一行（`remove`） | 103 | 103 |
| 表单一次提交（`set`） | 222 | 216 |
| 翻页（`create` + 两行种子 `append`） | 2 761 | 2 625 |
| 信封本身（一个 `empty` op） | 70 | — |
| 之后每多一个 `empty` op | 21.0 | — |

读法：信封 70 B 是固定成本，一个空 op 21 B 是每 op 的边际成本。**翻页那一帧 2.7 KB 是这一组里最贵的**，
它是结构帧（整棵树），而它本来就低频——DESIGN「操作」里认下的正是这一条：结构贵、数据便宜。

## 二、一个回合改多少 DOM

页内挂 `MutationObserver`（`childList` + `characterData` + `subtree`，不看 `attributes`），一帧落地后数
变更条数。

| 回合 | 变更条数 | 等它落地的那个 DOM |
|---|---|---|
| 窄：`set` 一个数据槽 | **1** | 槽里那个文本 |
| 列表：`append` 一行 | **1** | 新行 |
| 整树：`create` | **12** | 新树的根 |

读法：这就是「一帧一个事务、改动只落在它指向的那个平面」的**实测形态**——`set` 与 `append` 各一条变更，
整树替换才是一批。DESIGN 在 T3 里对旧壳断言过同一件事（「改一处槽只重算读它的组件」），这是新页上的数字。

## 三、首屏与资产

| 什么 | 大小 / 时间 | 口径 |
|---|---|---|
| 钉住的渲染器包 | 2 420 114 B | `versions.json` 里四件之和（js + wasm + 两个 css） |
| reflux 自己的资产 | 4 717 B | `reflux.css` + `reflux.js` |
| 文档开始 → 树画出来 | **16 ms**（三次：18 / 16 / 16） | 页内脚本记 `performance.now()`，4 ms 轮询 `#main` 有子节点 |
| DOMContentLoaded | **12 ms**（三次：12 / 10 / 12） | `PerformanceNavigationTiming` |

读法：本机、无头、资产走本地回环。**没有量的是**「深链多等一次连接往返值多少毫秒」——那要和服务端渲染的
形态并列才有意义，而那个形态已被 Why Not 否掉，单数字没有结论。资产体积按 DESIGN 明确**不作判据**，这里只
记录，不评价。

## 四、服务端 CPU（100 会话 × 50 帧/秒）

客户端跑在**子进程**里（100 条真 socket、每条按速率发 `name.change` 一类上行并读回下行），所以
`process_time` 量的是服务端自己；分母用**帧数**，不用秒数。

| 什么 | 值 | 口径 |
|---|---|---|
| 连接建立 | 100 / 100 | 全部落地 |
| 会话存活（峰值） | 100 | 每 50 ms 采样 |
| 处理帧数 | 24 472（目标 ~25 000，97.9 %） | 派发到处理器的上行帧 |
| 拒收 | 0 | 非零就说明这组数字不干净 |
| 服务端 CPU | 2.43 s | 窗口 6.6 s 的 `process_time` |
| **每帧** | **99 µs** | 仅服务端；客户端在别的进程 |
| 持续速率 | 3 699 帧/秒 | 客户端与服务器同机，所以这是**天花板**，不是吞吐承诺 |

读法：DESIGN 在 Why Not 里否掉「服务端持界面状态 + 每事件重渲染」时引的是 **0.37 ms/回合/会话**、并算出
「100 会话 × 50 事件/秒 = 两核」。这一轮的形状（服务端只发操作）实测 **99 µs/帧**，同样的负载约 **0.5 核**——
差的那一档正是「服务端不画界面」换来的，现在有数字了。

## 五、那两笔认下的代价（M1.5 的双份走查）

离线，各 3000 次取均值。**跨运行会抖**（下面括号里是两次运行的范围），所以只看量级：

| 调用 | 每次 | 做的事 |
|---|---|---|
| 建一个 `set` op（`wire.set`） | **4.2 µs**（4.2 – 11.0） | 闭集走查 + `parse` + `dump` |
| 出帧那道门（`ingest.check_frame`） | **3.4 µs**（3.4 – 7.3） | 同一个闭集走查再来一遍，在 socket 前 |
| 入站那道门（`ingest.check_uplink`） | **0.2 µs** | 只校形状，没有节点 |

结论：双份走查一帧约 3–4 µs，占 99 µs 的 **3–4 %**。M1.5 认下这笔代价时写的是「量级归 T11 测」——量完了，
它**不是**主要成本（主要成本在 JSON 编解码与 socket 往返），所以不需要缓存、也不需要把闭集表预热。

## 六、怎么读这些数字（方法上的界限）

- **只在一台机器上横比**。CPU 与首屏受温度、其它进程、频率影响；上面每组都是同一进程内的中位数（首屏三次、
  微基准 3000 次），目的是压掉抖动，不是伪造精度。
- **分母永远是帧**。用秒做分母会把「客户端发得慢」读成「服务器快」。
- **这一轮不改任何东西**。数字不好看是下一轮的设计问题（例如帧字节真的成了瓶颈），不是在这里加缓存的理由。
  记录在案的「认下的代价」只有一条改成有条件：双份走查若涨到可观比例（比如闭集扩大到几百个键），再谈缓存。
