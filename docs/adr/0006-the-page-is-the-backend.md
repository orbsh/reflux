# 0006 — 页面由后端画：交互是依赖追踪，而状态只有一份

Status: **Accepted**（2026-11-27），**已落地**：`reflux/signals.py` 的 `Signal`／`Computed`／`Effect`、`ctx.turn()` 与 `wire` 的八个操作就是这个决定的机制面；信号层自己的规矩在 ADR 0005，异步处理器在 ADR 0002。

## 1. 需求

交互是 UI 里难的那一半。把一份文档画出来是纯函数：输入定了，输出就定了。麻烦的是让一块**活着的屏幕**跟一份**活着的模型**保持一致 —— 模型会被点击、定时器、socket、数据库改，而屏幕必须跟上，且不能靠人肉记住"改这个值要重画哪些地方"。

传统前端的做法把它拆成两半：模型在后端，屏幕在前端，中间是一层 API。这种拆法不消灭复杂度，只是把它搬到**维持两份模型一致**上：

- 每个屏幕一个 JSON 形状，领域对象到它一次翻译，它到视图状态又一次翻译；
- "屏幕显示什么"因此有第二个可能出错的地方（前端那份拷贝会漂）；
- 拆法还决定了**什么能在哪里被答**：服务端记得的事要过一趟契约，客户端已经有的则是会漂的拷贝。

所以真正要回答的问题只有一个：模型变了，**什么重画、谁来决定**。

## 2. 决定

**依赖追踪**（MVVM 那一族）来回答，而它的机器**跑在后端**。

- **值记录读者，而且两跳都很细**：谁在追踪上下文里读了它（`Computed`／`Effect`），谁就订阅，它变了正好重跑那些读者；绑了槽的值则把槽写下去，读那条槽的节点由渲染器重画。没有依赖数组要维护，也就没有"依赖数组和代码不同步"这种错，更没有一棵树要比较。
- **没有树比较**：更新是操作（`set` 一条槽、`append` 一行、`patch` 一个指针），列表的身份由行的 id 决定，所以换位是一条 `move`，不是重建。实测一次 `set` 一条 DOM 变更、一次 `append` 一条（`docs/PERF.md`）。
- **页面没有自己的模型**：页面持节点与槽表，不持领域对象。处理器与模型在同一侧 —— 它可以查库、调模型、走对象图，然后把读到的值写回信号；读这些值的节点跟着重画，别处不必被通知。
- **一次投递一个 `ctx`**：`ctx.turn()` 把几次写收成一帧，客户端同时看到（ADR 0002 §9）。

屏幕上的一切因此是**这条连接状态的一次投影**，不是一份独立的状态副本。拷贝不存在，"两份状态不一致"这类 bug 也就没有地方长。

## 3. 为什么是依赖追踪

- **粒度落在读的地方**：写的人说的是"这个值是什么"，不是"哪些地方要变"。页面变复杂时，这句话的价值随复杂度上升 —— 手写 `set` 的地方越多，漏写一处就越贵。
- **不需要 diff**：读的地方就是重跑的边界，没有一棵虚拟树要比较，也没有"key 写错导致复用错节点"这一族问题。
- **比较是值相等**：相等的写不算变（`Signal` 的规则），所以"每次绘制都写一遍"不产生帧 —— 页面的写法可以退化到最笨的那种，代价仍是零帧。
- **依赖由运行时收集**（`Computed`／`Effect` 这一层）：读了什么就订阅什么，条件分支里读什么，就只在那个分支订阅什么 —— 不需要一张手写的依赖表。页面那一层不走追踪，走的是声明（绑了哪条槽），所以"一个值到页面的哪一处"仍然读得出来。

## 4. 为什么不是别的

- **客户端 SPA + JSON API**（最常见的那个）：能力不缺，缺的是"只有一份状态"。它把交互复杂度换成"同步两份模型"：契约形状、两层翻译、以及前端那份会漂的拷贝。每一次需求变化都要动两侧。
- **SSR + hydration**：首屏确实由后端画，但之后仍要一份前端状态接着跑 —— 同样的两份模型、同样的序列化边界，只是省了第一趟往返。
- **薄壳 + 客户端的依赖追踪**（Solid／Svelte 那一类）：追踪的机制对了，追踪的对象是浏览器里的那份状态；数据仍要靠 API 搬过去，两份模型的问题原样存在。
- **后端返回 HTML 片段**（htmx 那一类）：粒度是"片段"，换哪一段由写的人决定 —— 依赖追踪把这件事交给读的地方，而且值是类型化结构，不是字符串拼接。
- **处理器手写帧、不要信号**：那就是人肉维护依赖，页面一大就会漏；信号层保留手写入口（`slot.set(节点)` 原样通过，ADR 0005 §5），却没有把"记住依赖"退还给写的人。
- **让前端直接连数据库**：不可行，也不该 —— 那是把凭据与查询送到客户端。这一条只是说明上面那个"后端就是页面所在的地方"不是偏好，是权限与数据所在的位置。

## 5. 代价

认下的四条，README 的同名小节与这里说的是同一件事：

- **一次交互一次往返**：没有本地乐观更新（除非应用自己写），没有离线。
- **连接断了画面就停**：心跳会判死（`App.stats` 的 `dead`），重连是重画；这不是"渐进增强"的页面。
- **渲染器是一份钉住的 wasm**：界面自由度受词表约束 —— 能画什么由 accrete 的类型与属性决定。
- **每次点击都是一次 Python 调用**：`async` 处理器让它不挡别的连接（ADR 0002），但慢查询仍然是慢交互，该进后台的还是进后台。

还有一条更细的：**依赖收集只在一轮绘制之内**。跨绘制的生命周期要显式声明（`.store(key)`、`bind` 的首写等，ADR 0005），不是"追踪会自动记住"。这是有意的：一页声明了什么值、活多久，读代码的人要能看见。

## 6. 不做

- **不内置乐观更新与冲突合并**：那是应用对一致性的判断（谁能覆盖谁），框架只提供"写值 → 读者重画"。
- **不把领域对象序列化给页面**：页面拿节点与槽；能穿过线上的只有 JSON 值，且节点不是事实（ADR 0005 §3）。
- **不发明第二套模板语言**：页面是用 Python 写的树，没有模板语法与模板编译 —— 也就不存在"模板与模型对不上"这一类错。
- **不为"离线优先"留后门**：那会重新引入一份客户端模型，正是这份记录否掉的东西。

## 7. 落地与证据

- 机制：`reflux/signals.py`（三种信号、`batch`、`drawing` 的首写延迟）、`reflux/application.py` 的 `ctx.turn()` 与 `_draw`、`reflux/wire.py` 的八个操作。
- 页面：`examples/zh/demo_counter.py`（一个值、一条列表、三条 `store`）与 `examples/zh/demo_app.py`（值是每连接一张表、处理器按名字调用）。
- 门：`tools/gate_t2.py`（每个操作各一条 DOM 断言）、`gate_t9.py`（参考应用端到端，含后端认证）、`gate_t10.py`（两个语言的帧逐字节相等）、`tools/measure.py`（一次 `set` 一条 DOM 变更）。
